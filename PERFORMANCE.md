# Performance changes and deployment

Deploy all changed files together, including `scripts/`. Before routing traffic to the new version, run `php scripts/migrate.php` with the production PHP installation and the same DB_DSN, DB_USER and DB_PASS environment used by PHP-FPM. `update.sh` now runs this step after pulling. Back up the database before upgrades. The migration preserves the existing legacy upgrades and backfills, and adds composite analytics indexes and an evidence date index. It requires DDL privileges; normal requests no longer do. It upgrades an existing database, not an empty installation. Do not run simultaneous migrations.

Normal requests no longer execute schema checks, ALTER/CREATE commands, settings/tag seeds, or username backfills. A read-only redaction schema probe remains so evidence protection fails closed if that table is unavailable.

Archived cases require the updated status-enum migration (`php scripts/migrate.php`). Administrators can archive a case from its case page or status selector. Archived cases appear in Case Reviews, are excluded from public listings/search and direct case/evidence access, and support the existing revocable seven-day private links. Archive warnings appear on the case, evidence viewer, standalone evidence previews and sharing controls. Restoring a case returns it to Being Built and revokes its archive link; approval is required before publication.

Deploy `photo.php`, `lib/case-photo-http.php`, and `uploads/people/.htaccess` together with these changes. Photos now require a case-visibility or scoped-link check before serving either originals or cached thumbnails; photo responses are no-store. Raw `/uploads/people/` files must never be served directly. Apache inherits the uploads-level denial; any nginx/OpenResty/static-file/CDN rule that bypasses Apache must deny this directory too (for example `location ^~ /uploads/people/ { return 404; }`). Purge previously cached `photo.php` responses and `/uploads/people/` assets when deploying this change so old public photo caches cannot outlive archiving. Already downloaded copies cannot be recalled.

The public cases grid displays 24 cases per page with Previous/Next links preserving search and tag filters. View counts and tags are fetched in batches for that page. Images load lazily and video previews do not fetch metadata until needed. Apache compresses text responses where mod_deflate is installed, and caches public CSS/JS/fonts where mod_expires is installed.

Page-view analytics retain request and device data, scoring and alerts, and geo headers supplied by the edge. Page loads no longer call the external GeoIP service; ISP/proxy/location enrichment can be populated separately with the existing `backfill_case_views_geoip.php` CLI job. Submission metadata still performs its deliberate GeoIP lookup. Proxy/hosting-based alerts on a new view will only have header/basic data until separate enrichment; the existing backfill does not recompute alerts.

Validation here is local syntax and isolated behavior checks (`php tests/performance.php`). Production database query plans, timings, Apache configuration, and browser behavior need verification on the deployed environment. Compare cases, a case detail, evidence thumbnails, and authenticated admin requests before/after with cold and warm caches; confirm pagination/filter links, redacted evidence, analytics updates and account actions. The remaining recent-activity ordering aggregates evidence by case; large databases may benefit from a transactionally maintained activity column after query-plan measurement.

## Second performance pass

The public homepage measured approximately 0.08 seconds to first byte and 6.01 seconds to finish its 188 KB HTML response before this pass. This is one unauthenticated network sample, not an attribution of all six seconds to PHP. It confirms that reducing image downloads alone is insufficient.

Deploy `photo.php`, `lib/photo-thumbnails.php`, `lib/case-photo-http.php`, `uploads/people/.htaccess`, `assets/site.css` and the updated `index.php` together. PHP GD generates WebP previews (JPEG fallback) in `uploads/people/thumbnails`; PHP needs write access there. The endpoint uses 160/640/1200-pixel bounds and versioned URLs, and checks case visibility or private-link validity before every response. Browser responses are no-store so archiving or link expiry takes effect on subsequent requests. Missing GD or cache write permission falls back to streaming the already-authorized original. Cards use responsive images; the first two are eager and the rest lazy. Small case avatars and game sprites use 160-pixel previews. Source changes invalidate generated previews; superseded cached files may be periodically removed to reclaim disk space.

Evidence previews are encoded at quality 78 and cached in the existing private evidence directory. Every cache hit still passes the evidence authorization and public-redaction freshness checks. Content hashes and rotation invalidate the cache. Restricted whole-image blur retains its original path. No private evidence cache is published as static assets.

Page-view capture/scoring/alerts now run in the existing browser analytics POST after DOMContentLoaded. A short-lived one-use session ticket ties that POST to a page that was actually rendered and preserves its URL/referrer context. The session lock is released before analytics queries. Views from browsers with JavaScript disabled, blocked requests or interrupted loading are no longer counted. Failed capture is best effort, without retries. Homepage tracking skips case-level history scans.

The shared stylesheet is now a versioned static file. jQuery, DataTables and Select2 are loaded only on pages using those controls. Existing text compression/cache rules apply to the new CSS.

Checks: `php tests/performance.php`, `php tests/photo-thumbnails.php` and PHP lint. A synthetic 1800x1000 PNG of 5,409,722 bytes produced 160/640/1200-pixel previews of 6,030 / 82,052 / 181,806 bytes on the local GD installation. Actual sizes depend on the photo.

Next server checks if latency remains: measure response completion and database query plans after deployment; verify PHP OPcache is enabled for PHP-FPM; verify gzip/Brotli at the serving proxy; inspect PHP-FPM worker saturation and MySQL connection latency; confirm the prior composite indexes were installed. The recent-activity listing still aggregates evidence, so measure that query before adding an activity rollup. Whole-page caching needs account/CSRF-aware design because this application mixes public pages with session state.

## Large evidence uploads

Deploy `.user.ini` together with the upload handlers. It allows files up to 500 MB with a 510 MB total POST limit and an hour for incoming request data. PHP-FPM may cache `.user.ini` for several minutes; reload the relevant FPM service to apply it immediately. The uploader displays the effective limit from the web PHP process and rejects larger files before sending them. PHP CLI settings can differ from FPM settings.

The live site also uses an OpenResty reverse proxy. Its request-body limit must allow the complete request, for example `client_max_body_size 510m;` in the site's nginx/OpenResty server or proxy location. Apply that setting at every proxy in front of PHP and validate/reload the affected nginx configuration. PHP cannot override an upstream HTTP 413 rejection. Also ensure the PHP upload temporary directory and private evidence storage have enough free space for the incoming and stored copies.

Validate with `php tests/evidence-uploads.php --large` for an actual 400 MB multipart upload plus content-hash verification, and `node tests/evidence-upload-response.js` for HTML/413, timeout, malformed-response and JSON error handling. These checks use isolated local storage and a test server; they do not change live proxy configuration.
